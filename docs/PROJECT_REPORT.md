# Weather NUU — технический отчёт о проделанной работе

> Материал для дипломной работы. Описывает систему мониторинга микроклимата
> (weather.nuu.uz): что было изначально, какие проблемы обнаружены, как они
> решены на стороне бэкенда и фронтенда, какие результаты получены.
> Числа и наблюдения актуальны на **25 сентября 2026** (замеры на боевом сервере).
> Код бэкенда живёт в отдельном репозитории `weather-backend`
> (монорепозиторий), фронтенда — в этом репозитории.

---

## 1. Что это за система

Университетская система мониторинга условий в аудитории и на улице.

* **Датчики** — микроконтроллеры ESP32 (два комплекта: `room` — аудитория,
  `street` — улица). Каждые ~5 секунд отправляют HTTP POST с показаниями:
  температура, влажность, давление и два газовых датчика (в интерфейсе они
  отображаются как «углекислый газ» — поле `mq5`, и «аэрозоль PM2.5» — поле `mq3`).
* **Бэкенд** — принимает показания, хранит их в PostgreSQL, отдаёт историю,
  агрегаты и экспорт, рассылает обновления по WebSocket.
* **Фронтенд** — веб-дашборд (React): текущие значения с цветовыми зонами нормы,
  интерактивные графики за произвольный период, экспорт данных, статус «живой ли датчик».

Схема потока данных:

```
ESP32 (room/street)                                   Браузер
   │  POST /api/room|street  (каждые ~5 с)              ▲   ▲
   ▼                                                    │   │ REST (latest, history, aggregate, export)
┌────────┐   /api/*    ┌──────────────────┐  SQL   ┌────┴───┴────┐
│ nginx  │────────────▶│ Fastify API (TS) │───────▶│ PostgreSQL  │
│ (TLS,  │  /v1/*      │  Docker :8002    │        │  15 (Docker)│
│ static)│◀────────────│  cron, WS, export│        └─────────────┘
└───┬────┘  WebSocket  └──────────────────┘
    │  /v1/ws/sensors  (push нового показания всем клиентам)
    └───────────────────────────────────────────────▶ Браузер
```

## 2. Исходное состояние и найденные проблемы

Исходная система — бэкенд на Python (планировщик APScheduler) и лёгкий
фронтенд на «чистом» JS, позднее перенесённый на React. Ниже — проблемы,
выявленные при разборе и эксплуатации. Часть найдена только при работе с
реальным «железом» и реальным боевым сервером — это отдельная ценность.

### 2.1 Проблемы старого бэкенда

| # | Проблема | Последствие |
|---|----------|-------------|
| 1 | Значения «подмешивались» по расписанию: раз в час клонировалась последняя запись, даже если датчик давно молчал | На графиках бесконечная плоская линия вместо честного «данных нет»; невозможно отличить «датчик выключен» от «ничего не менялось» |
| 2 | Колонка `timestamp` — наивная (`timestamp without time zone`), время хранилось «по умолчанию UTC» неявно | Хрупкость: результат зависит от таймзоны сессии/контейнера/драйвера; риск незаметного сдвига времени при любом изменении конфигурации |
| 3 | Нет индекса под основной запрос «по источнику и диапазону времени» | Выборка по PK-сканированию, деградация при росте таблицы |
| 4 | Ответы — «голые» массивы без пагинации | Нельзя корректно отдать миллионы строк, клиент либо получает обрезанную выборку, либо огромный ответ |
| 5 | Нет WebSocket — только периодический опрос | Задержка отображения = период опроса; лишняя нагрузка |
| 6 | Нет экспорта данных, нет обнаружения пропусков | Для анализа данные приходилось выгружать вручную из БД |
| 7 | Слабая типизация контрактов «бэк ↔ фронт», ручной разбор дат | Класс ошибок на границе слоёв (форматы, `null`, порядок) |
| 8 | Нет валидации входных данных и единого формата ошибок | Некорректные пакеты тихо попадали в БД |

### 2.2 Проблемы, обнаруженные при развёртывании и работе с реальными устройствами

Эти дефекты не видны в тестах — проявились только после запуска нового
бэкенда на сервере рядом с работающим старым.

1. **Маршрутизация прошивки.** Прошивки ESP32 (`Room/Street LAST.ino`)
   отправляют POST на «голые» пути `/api/room` и `/api/street` (форма старого
   бэкенда). В конфигурации nginx для этих путей не было `location`, запрос
   «проваливался» в SPA и возвращал `index.html` — устройство считало, что
   «сервер не принимает данные». Решение: точные `location = /api/room` и
   `location = /api/street` с проксированием на `/v1/sensors/...` нового API.
   Аналогично для `latest`/`all`, отдельно — WebSocket-upgrade и увеличенный
   `proxy_read_timeout` (600 с) для экспортов.
2. **Формат полей.** Прошивка шлёт `bmp_press` и `fused_temp` (snake_case), а
   контракт нового API — camelCase. Чтобы не перепрошивать уже развёрнутые
   устройства, в схему входных данных добавлен препроцессор (`z.preprocess`)
   с таблицей соответствий `bmp_press → bmpPress`, `fused_temp → fusedTemp`.
3. **Отсутствие `DEFAULT now()`.** Физическая колонка `timestamp` никогда не
   имела значения по умолчанию (старый бэкенд всегда задавал время явно).
   Новый бэкенд время не передаёт → каждый реальный POST падал с
   `NOT NULL violation`. Исправлено `ALTER COLUMN ... SET DEFAULT now()`.
4. **Тип времени в БД.** Drizzle-схема объявляла `timestamptz`, а фактическая
   колонка была `timestamp` без зоны — расхождение «тип в коде ≠ тип в БД»,
   совпадавшее лишь случайно (всё было в UTC). Выполнена миграция
   `ALTER COLUMN ... TYPE timestamptz USING ... AT TIME ZONE 'UTC'` для
   `sensor_data` и `cansat_data` на боевой базе: с предварительным `pg_dump`
   (≈102 МБ), проверкой отсутствия сдвига значений и без остановки приёма
   данных (устройства продолжали писать во время короткой блокировки).
5. **Датчик «Street» не присылал данных.** Анализ логов nginx (все ротации,
   7+ суток) показал **ноль** попыток POST — не ошибки, а полное отсутствие
   запросов. Это позволило доказать, что проблема на стороне устройства/сети/
   питания, а не сервера (тот же путь кода для `room` работал стабильно).
   Позже устройство ожило; по логам виден профиль: 15 часов устойчивой
   передачи (~721 запись/час), затем обрыв и «пачечная» работа — характерно для
   проблем питания или Wi-Fi на улице.

## 3. Бэкенд: рефакторинг и новая архитектура

### 3.1 Технологический стек

* **Node.js 20 + TypeScript**, фреймворк **Fastify** (быстрый, схемный).
* **Drizzle ORM** + **PostgreSQL 15**; миграции — `drizzle-kit`.
* **Zod** — единый источник истины для валидации и типов.
* **Turborepo + pnpm workspaces** (монорепозиторий).
* **ExcelJS** (потоковая запись XLSX), **archiver** (ZIP), **node-cron**
  (почасовой снимок), **@fastify/websocket**, **Vitest** (тесты).
* Развёртывание: **Docker** (multi-stage), **docker compose**, **nginx**.

### 3.2 Структура монорепозитория

```
weather-backend/
├─ apps/api/                    # Fastify-сервис
│  └─ src/
│     ├─ app.ts, server.ts, env.ts
│     ├─ db/            (schema.ts, client.ts, migrations/, manual/)
│     ├─ plugins/       (db, websocket, device-auth, error-handler)
│     ├─ modules/
│     │   ├─ sensors/   (routes → service → repo, aggregate.repo)
│     │   ├─ export/    (routes, service, repo, gap-detector, i18n)
│     │   ├─ cansat/    (тот же слоистый шаблон)
│     │   └─ health/
│     ├─ jobs/hourly-snapshot.ts
│     └─ lib/           (cursor, keyset, aggregate-bucket + тесты)
└─ packages/
   ├─ contracts/                # Zod-схемы, общие для бэка и фронта
   └─ tsconfig/                 # общая конфигурация TS
```

Принципы: слоистость `routes → service → repo` (HTTP отделён от бизнес-логики и
от SQL), плагины Fastify для сквозных задач, **общие контракты** в отдельном
пакете — форма запросов/ответов описывается один раз.

### 3.3 Ключевые улучшения

**Контракты и типобезопасность.** Пакет `@weather/contracts` содержит Zod-схемы
(датчики, агрегаты, экспорт, ошибки, события WebSocket). Из них выводятся
TypeScript-типы, они же используются для валидации и сериализации ответов.
Единый формат ошибок (`AppError`) и глобальный обработчик.

**Модель данных.**
* `timestamptz` (время с часовым поясом), `DEFAULT now()`.
* Составной индекс `(source, timestamp)` под главный запрос.
* Флаг `isSnapshot` — отличает «клон почасового снимка» от реального показания.
* Разделение «источников» (`room`/`street`) одной таблицей `sensor_data`.

**Честные пропуски вместо фальшивой непрерывности.** Почасовой снимок теперь
клонирует последнюю запись **только** если реальные данные приходили в
последние 3 часа (`MAX_SNAPSHOT_GAP_MS`). Дольше — не «выдумывает» данные:
пропуск остаётся пропуском. Решение о срабатывании принимается по последней
**реальной** записи (за это отвечает `isSnapshot`), иначе каждая копия
обнуляла бы собственный «таймер свежести». Планировщик привязан к UTC явно.

**Keyset-пагинация вместо OFFSET.** Курсор по паре `(recordedAt, id)`
гарантирует, что каждая строка будет выдана ровно один раз даже при
одинаковых метках времени; стоимость страницы не растёт с глубиной. Лимит
страницы — 10 000. Логика вынесена в `lib/keyset.ts` и покрыта тестами.

**Агрегирование на стороне БД (`/v1/sensors/:source/aggregate`).**
Интервальные корзины через `date_bin(interval, ts, origin)` (а не
`date_trunc` — корзины вроде 15 мин или 3 ч не являются календарными единицами).
Для каждого показателя возвращаются `avg/min/max` и `count`. Функция
`resolveAutoBucket(spanMs)` выбирает самую мелкую корзину, при которой в
ответе не более ~1500 точек (`AGGREGATE_TARGET_POINTS`); она вынесена в общий
пакет контрактов и покрыта 10 модульными тестами. Отдельная деталь: в сыром SQL
псевдонимы обязаны быть в двойных кавычках (`"bmpPress_avg"`), иначе Postgres
приведёт идентификатор к нижнему регистру.

**Потоковый экспорт (`/v1/export/...`).**
* Форматы: **CSV** (с BOM для корректного открытия в Excel на русской
  локали, колонка `kind` — reading/gap), **XLSX** (два листа: «Показания» и
  «Пропуски», локализованные заголовки ru/uz/en), **ZIP «по месяцам»**
  (по файлу на месяц + `summary.csv`).
* Данные читаются из БД keyset-страницами и пишутся в поток — потребление
  памяти не зависит от объёма.
* **Детектор пропусков** (`gap-detector.ts`) — чистая функция, вставляет
  явные маркеры «пропуск от…до…, примерно N потерянных показаний» между
  соседними записями, если разрыв больше порога. Покрыта тестами
  (граничные случаи: пустой поток, первая строка, ровно порог).
* Отдельный `meta`-эндпоинт для границ данных (нужен UI выбора месяцев).

**WebSocket (`/v1/ws/sensors`).** При приёме нового показания сервер рассылает
событие подключённым клиентам (in-process pub/sub; при масштабировании на
несколько реплик заменяется на Redis без изменения мест вызова).

**Безопасность записи.** Плагин `device-auth`: заголовок `x-api-key`
проверяется сравнением с постоянным временем (`timingSafeEqual`). Осознанный
компромисс — отсутствие заголовка допускается (логируется), потому что старая
прошивка его не шлёт, а полная обратная совместимость — жёсткое требование.
Ключ и `CORS_ORIGIN` валидируются при старте (пустой CORS не допускается —
отсутствие значения должно ронять запуск, а не открывать API всем).

**Совместимость со старыми клиентами.** Legacy-пути nginx-ом
транслируются на новые маршруты; форма ответов новых эндпоинтов отличается
(`{ items, nextCursor }`), фронтенд принимает обе формы.

### 3.4 Развёртывание

* Многоэтапный **Dockerfile**: `turbo prune` вырезает минимальный
  подмножество монорепозитория, слой зависимостей кэшируется и
  пересобирается только при изменении зависимостей; итоговый образ
  запускается через `tsx` (пакет контрактов поставляется как TS-исходники).
* `docker compose`: сервис `api-new`, healthcheck (`/v1/health`), политика
  `unless-stopped`, подключение к уже существующей сети БД.
* Новый бэкенд работает **параллельно** старому (другое имя контейнера,
  порт 8002), переключение — на уровне nginx: безопасный откат.
* Доступ к серверу — через VPN + SSH; на каждом деплое — резервная копия
  (`nginx`-конфигурации, статики фронтенда, дамп БД перед миграцией).

### 3.5 Тесты

Vitest: `resolveAutoBucket` (10 кейсов), кодирование курсора, keyset-условие,
детектор пропусков. Тестируется чистая логика, не требующая БД.

## 4. Проблема: «Всё», 24 ч и 7 д — пустые/медленные графики

Симптом: при выборе «Всё» и коротких диапазонов график был пуст или строился
очень долго. Причины (найдены последовательно):

1. Клиент получал только **первую страницу** (10 000 строк) — для «Всё» она
   заканчивалась апрелем, хотя данные шли до сентября. Исправлено циклом
   пагинации по `nextCursor` (потолок `MAX_TOTAL = 2 000 000`).
2. Форма ответа нового бэкенда (`{ items, nextCursor }`) отличалась от
   «голого массива» — маппер знал только `data`/массив; добавлен `items`.
3. Для широких диапазонов клиент делал **100+ последовательных запросов** —
   слишком дорого.

**Решение архитектурного уровня — разделение «сырых» и «агрегированных»
данных:** короткие диапазоны (1 ч, 6 ч, 24 ч) обслуживаются живым кэшем на
клиенте (без запроса), длинные (7 д, 30 д, 90 д, «Всё», произвольный период
> 7 суток) — одним запросом к `/aggregate` (≈1500 точек). Это заменило десятки
запросов и мегабайты данных единичным ответом порядка десятков килобайт.

## 5. Фронтенд

### 5.1 Что представляет собой фронтенд

Одностраничное приложение (SPA) — **дашборд реального времени** двух комнат
датчиков. Два маршрута (`/` — аудитория, `/street` — улица) на общем макете.
Показывает:

* карточки текущих значений с **цветовыми зонами нормы** и ползунком-маркером
  (температура, влажность, давление, углекислый газ (mq5), аэрозоль (mq3));
* индикатор «LIVE / данные устарели» (см. 5.5);
* интерактивный график показателя за выбранный период;
* экспорт данных; переключение языка (**ru / uz / en**) и темы (светлая /
  тёмная / системная).

### 5.2 Стек

React 19, TypeScript 5.7, Vite 6, **TanStack Query 5** (серверное состояние,
кэш, опрос), **ECharts 6** (`echarts-for-react`) для графиков, Tailwind CSS 3 +
примитивы **shadcn/ui** (Radix), i18next, framer-motion (анимации), sonner
(уведомления), react-day-picker (календарь), axios, hls.js (видеопотоки).

### 5.3 Архитектура (Feature-Sliced Design)

```
src/
├─ app/         провайдеры (query, i18n, тема, router, toaster, error boundary), стили
├─ pages/       страницы: dashboard-room, dashboard-street, 404
├─ widgets/     составные блоки: dashboard-layout, weather-summary,
│               sensor-charts, topbar, language-switcher
├─ features/    пользовательские сценарии: chart-selector, time-range-selector,
│               date-range-picker, export-data
├─ entities/    домен «weather»: api/, model/ (типы, маппер, пороги, свежесть)
├─ shared/      api (http), config (env), lib (даты, форматирование, цвета), ui
└─ components/ui/  shadcn-примитивы (button, dialog, radio-group, …)
```

Слои зависят только «вниз» (страницы → виджеты → фичи → сущности → shared).
Домен изолирован в `entities/weather`: остальной код не знает деталей API.

### 5.4 Как фронтенд получает и обрабатывает данные

**Три источника, один кэш.** Все данные попадают в единый кэш React Query:

1. **REST-опрос** `latest` (каждые 10 с) — базовый механизм.
2. **WebSocket** `/v1/ws/sensors` — push нового показания сразу; пишет в тот
   же кэш. Опрос при этом остаётся включённым как «страховочная сетка»: если
   сокет недоступен или оборвался, данные всё равно идут. Реализованы
   автопереподключение (3 с) и «поколения» сокета, исключающие дублирующие
   подключения после рестарта сервера (иначе на графике появлялись
   задвоенные точки).
3. **Полная история** раз в 5 минут — на случай пропущенных точек.

Новая точка из `latest` **дописывается** в кэш истории без повторного запроса;
размер живого кэша ограничен (3000 точек) — иначе долгая сессия росла бы
бесконечно и каждое добавление перерисовывало весь график.

**Диапазоны.** `1ч/6ч/24ч` — клиентская фильтрация живого кэша; `7д/30д/90д` и
произвольный период — серверный `aggregate` (для произвольного периода ≤ 7 суток
— «сырые» данные с пагинацией: точность почти бесплатна, выше порога
агрегат передаёт тот же визуальный сигнал гораздо дешевле).

**Защита от «мусорных» данных.** Прошивка датчика в прошлом присылала
метки времени в секундах вместо миллисекунд (даты ≈2001 года). Фильтр
`MIN_VALID_TS` (2020-01-01) отсекает такие записи; точкой отсчёта «последних N
часов» служит максимальная **валидная** метка, а не последний элемент массива.

### 5.5 Индикатор «датчик живой?» (freshness)

Возраст последней записи сам по себе недостаточен — бэкенд мог «освежать»
метку клонами. Поэтому оценка **по данным**: считается, сколько времени
подряд последнее значение не менялось во **всех** полях. Порог — 10 минут
(`MIN_STUCK_DURATION_MS`); старше 3 ч — «оффлайн».

Ранее правило было по числу точек (3 одинаковые подряд) — давало ложные
срабатывания: SQL-анализ боевых данных показал, что у полностью исправного
датчика из-за квантования бывают серии одинаковых значений до ~35 с несколько
раз в час. Порог 10 минут даёт ~17-кратный запас над наблюдаемым шумом и
не зависит от частоты отправки (5 с у реальных устройств, 1 ч у клонов
старого бэкенда). Логика проверена автономным Node-скриптом на 4 сценариях до
выкладки.

### 5.6 Графики (ECharts)

* Линия показателя с **оценкой границ**: в агрегатном режиме дополнительно
  рисуется полоса min–max (приём «невидимая накладываемая линия» + заливка).
* **Выборка LTTB** (`sampling: "lttb"`) для сырого режима — сохраняет форму
  кривой при прореживании.
* **Разрывы на пропусках:** между соседними точками с интервалом > 90 мин
  вставляется `null` — линия обрывается вместо ложной интерполяции через недели
  тишины, а зона пропуска подсвечивается (`markArea`). Тот же принцип «не
  выдумывать непрерывность», что и в экспорте бэкенда.
* Масштабирование/панорамирование (`dataZoom`), кнопки «сбросить масштаб» и
  «сохранить как изображение» (`toolbox`).
* Исправленный дефект: при переключении диапазона (напр., 90д → 24ч)
  сохранялся масштаб старого диапазона — ECharts в режиме слияния опций
  помнит `dataZoom`. Решение: составной `key` компонента включает идентификатор
  диапазона, график пересоздаётся.
* Подпись последнего значения округлялась до 0,1 и «маскировала» реальные
  изменения, видимые в подсказке (0,01) — формат унифицирован до 2 знаков.
* Единый источник истины для порогов: границы зон карточек и статус-бейджи
  выводятся из одной таблицы `SENSOR_RANGES`, поэтому бейдж не может расходиться
  с положением ползунка (ранее у MQ-датчиков были свои «ручные» пороги).

### 5.7 Экспорт на клиенте

Меню «Скачать»: «Весь период», «Выбранный период» (запрос через календарь),
«Выбрать месяцы…» (модальное окно, сетка по годам; месяцы до начала данных
и будущие отключены; формат по умолчанию — XLSX, доступен CSV).

* **Индикатор прогресса** — единый тост, обновляемый по потоку байт
  («Скачано X МБ из Y МБ»).
* **Автоповтор** (`downloadExport`): до 3 попыток с паузами 1 с / 2 с.
  Причина: Fastify фиксирует код 200 и заголовки **до** того, как асинхронный
  генератор выгрузки сможет упасть, поэтому нестабильное соединение выглядит
  как оборванный chunked-ответ (`ERR_INCOMPLETE_CHUNKED_ENCODING`), а не как
  чистая ошибка; раньше помогал ручной повторный клик. Теперь повтор
  автоматический, а тост показывает «(попытка N)», чтобы обнуление счётчика не
  выглядело как порча данных.
* **Проверка целостности:** боевые проверки показали, что экспорт всегда идёт
  `Transfer-Encoding: chunked` без `Content-Length`, поэтому «сверка с
  content-length» здесь бесполезна. Для XLSX/ZIP проверяется наличие
  **трейлера ZIP** (`PK\x05\x06`) в конце файла — усечённый архив не будет
  сохранён как «успешный».
* Освобождение читателя потока (`releaseLock`) при ошибке; каждый повтор
  перекачивает файл с нуля (возобновление с середины потребовало бы
  перестройки генератора экспорта на сервере — сознательный компромисс).

### 5.8 Время в XLSX

В скачанном файле колонка «Время (UTC)» показывала только дату. Значение
ячейки содержало полное время (серийная дата Excel), но формат отображения
был встроенный «краткая дата» (`numFmtId=14`): потоковый `WorkbookWriter`
ExcelJS с `useStyles:false` **молча отбрасывал** пользовательский формат
`yyyy-mm-dd hh:mm:ss`. Исправление — `useStyles:true`. Замер: размер файла
не изменился (+62 байта на 15,4 МБ), потому что стиль один на колонку, а не
на ячейку. Проверено разбором сырого OOXML (`styles.xml` теперь содержит
`numFmt 164`, ячейки ссылаются на него).

### 5.9 Интерфейс и доступность

* Диалог выбора месяцев — на `Dialog` shadcn (непрозрачный фон вместо
  «стеклянного», через который просвечивал график), выбор формата —
  `RadioGroup`; выбранный пункт залит акцентным цветом.
* Найдена **корневая причина «острых углов» кнопок и невидимого состояния
  радиокнопки**: компоненты shadcn сгенерированы под **Tailwind v4**
  (`@custom-variant data-checked`, `var(--radius-md)`), а в проекте **Tailwind
  3.4**, который эти конструкции молча игнорирует (`--radius-md` не определён →
  радиус нулевой; `data-checked:` вообще не компилируется). Исправлено на
  v3-совместимые `rounded-md` и `data-[state=checked]:`. Побочное следствие,
  оставленное на будущее: анимации `data-open/data-closed` в примитивах Dialog
  также «мёртвые».
* Три языка (ru/uz/en) для всех строк, включая тосты, экспорт и месяцы.
* Тема (светлая/тёмная) и подсказки состояния; кнопки/цели соответствуют
  рекомендуемым размерам касания.

**Данные.** ~1,69 млн записей (room ≈ 1,20 млн, street ≈ 0,49 млн), период с
декабря 2025; размер БД 347 МБ (таблица 339 МБ, индексы 189 МБ). Прирост
≈ 25 тыс. строк в сутки (~9 млн в год).

**Стабильность.** Контейнер API работает с 21 сентября без перезапусков и
OOM; CPU 0,1–0,7 %, память 135–190 МБ из 3,8 ГБ. За 48 ч — 0 ошибок в логах.
Почти все запросы nginx — 200/201/304; единичные 400/405 — сканирующие боты
(`/etc/passwd`, `cgi-bin`, `phpunit`), корректно отсекаются; два 408 —
таймауты со стороны ESP32.

**БД.** Кэш-попадания 99,82 %, взаимных блокировок 0, длинных транзакций нет,
2 соединения из 100. После миграции типа времени статистика планировщика
устарела (147 тыс. вместо 1,69 млн строк) — обновлена `ANALYZE`.

**Нагрузочная проверка** (локально на сервере, все ответы 200):

| Запрос | Параллельность | p50 | p95 |
|--------|---------------|-----|-----|
| `/latest` (400 запросов) | 25 | 3 мс | 29 мс |
| `aggregate` за 7 суток | 10 | 0,38 с | 0,62 с |

**Экспорт.** Один месяц XLSX (~15,4 МБ) скачивается потоком; прогресс

| Область | Проблема | Решение |
|---------|----------|---------|

| Бэк | Нет индекса под основной запрос | Индекс `(source, timestamp)` |
| Бэк | OFFSET/обрезанная выборка | Keyset-пагинация `(recordedAt, id)` |
| Бэк | Нет агрегатов, 100+ запросов на широкий диапазон | `date_bin`-агрегаты + авто-корзина ≤1500 точек |
| Бэк | Нет экспорта/пропусков | Потоковый CSV/XLSX/ZIP + детектор пропусков |

| Бэк | Ручная типизация | Общий пакет Zod-контрактов |

| Инфра | `NOT NULL` на каждом POST | `SET DEFAULT now()` |

## 8. Выводы и ограничения

**Что дал рефакторинг.** Прозрачность данных (пропуск виден как пропуск),
корректные времена, масштабируемая выдача (keyset + агрегаты), «живой»
интерфейс (WebSocket с запасным опросом), пригодность данных для анализа
(экспорт с явными пропусками), типобезопасные границы между слоями и
воспроизводимое развёртывание (Docker/`turbo prune`, откат через nginx).

**Методологический опыт.** Многие дефекты — маршрутизация прошивки,
отсутствие `DEFAULT`, конфликт версий Tailwind, ложная работа «проверки по
content-length», потеря формата XLSX — не ловятся типизацией и юнит-тестами;
они найдены только проверкой на реальных устройствах, боевом сервере и
разбором сырых артефактов (заголовки HTTP, XML внутри XLSX, SQL-статистика).
Исправление ошибочного собственного вывода («в XLSX время уже есть») после
получения контрпримера — пример практики «проверять, а не предполагать».

**Ограничения и дальнейшая работа.**

* Автоповтор экспорта перекачивает файл с нуля; настоящее возобновление
  требует поддержки диапазонов на сервере.
* Для CSV нет встроенного признака полноты (в отличие от ZIP-трейлера).
* Историю «за всё время» при росте таблицы свыше 5–10 млн строк стоит
  строить по предагрегированной (почасовой) таблице.
* Анимации `data-open/data-closed` в примитивах shadcn (сгенерированы под
  Tailwind v4) не работают на Tailwind v3 — либо миграция на v4, либо
  переписывание на `data-[state=open]:`.
* Аутентификация записи мягкая (ключ необязателен из-за старой прошивки) —
  ужесточить после перепрошивки устройств.
* Отсутствуют автоматические интеграционные тесты с реальной БД и
  UI-тесты фронтенда.
* Для датчика `street` необходимо устранить причину обрывов
  (питание/Wi-Fi) — на сервере проблем не обнаружено.
