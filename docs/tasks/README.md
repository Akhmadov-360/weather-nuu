# Задания участникам: общие правила и карта зон

порядке идти**. Сами задания лежат рядом:

| Аналитика: качество данных, статистика, прогноз | группа №7 (Бахтиярова З., Курбаналиева Ш.) | [ANALYTICS.md](ANALYTICS.md) |
| Платформа: архитектура, приём данных, живой дашборд, инфраструктура, ревью | Ахмадов А. (владелец) | этот документ, раздел «Что делает владелец» |

Прочитайте до первого задания: `README.md`, `AGENTS.md`, `CONTRIBUTING.md` и **оба**

## 1. Из чего состоит система

```
 ESP32 (room, street) ──▶ API (weather-backend) ──▶ PostgreSQL
 внешние источники ─────▶   modules/sensors, export        │
   (адаптеры, Тулешов)      modules/stations, map, sources │   (Тулешов)
                            modules/analytics-*            │   (группа №7)
                                   │
                    @weather/contracts   @weather/air-quality   @weather/timeseries
                       (форма API)        (шкалы AQI)            (ряды, пропуски)
                                   │
                          Фронтенд (weather-nuu)
              дашборд (владелец) · карта (Тулешов) · аналитика (группа №7)
```

Три общих пакета бэкенда **нельзя дублировать**: форма данных API живёт в `@weather/contracts`,
шкалы AQI в `@weather/air-quality`, работа с рядами (регулярная сетка, пропуски) в
`@weather/timeseries`. Фронтенд намеренно не зависит от этих пакетов (сборка фронтенда не должна
ломаться из-за бэкенда), поэтому его типы и фикстуры копируются **вручную** и проверяются в PR.
Шкалы AQI там тоже есть (`src/shared/lib/air-quality/`), а совпадение с серверным кодом
доказывает общий файл эталонных значений `aqi-vectors.json` (P1, готово).

## 3. Правила стыка (как мы не мешаем друг другу)

1. **Контракт первым.** Первый PR любого нового API содержит только схему Zod, JSON-пример и тест,
   что пример проходит схему. После его влития бэкенд и фронтенд делаются параллельно и никто никого
   не ждёт: фронтенд работает по фикстуре, бэкенд отдаёт ту же форму.
2. **Миграции БД только у Тулешова.** Две параллельные миграции ломают нумерацию. Аналитика
   ничего не пишет в базу: считает по `sensor_data` на лету (SQL-агрегаты плюс чистые функции).
   Если вам понадобилась таблица, придите к владельцу, это решается отдельно.
3. **Переводы.** Каждая зона пишет только в свой файл-пространство имён (`map.json`, `analytics.json`,
   в `common.json` не добавлять), все три языка (ru, uz, en): `useTranslation('map')`. Это закрывает
   главный источник конфликтов при слиянии (P3 сделано).
4. **Не изобретать повторно.** Перед новой утилитой поищите в `packages/` и `src/shared/lib`:
   шкалы AQI, пропуски и сетка рядов, `resolveAutoBucket`, фильтры, форматирование уже есть.
5. **Тесты рядом с кодом, логика чистыми функциями.** Весь расчёт (IDW, AQI, статистика, прогноз)
   живёт в чистых функциях без базы и без React; маршрут и компонент тонкие. Это требование и
   архитектуры, и защиты: чистую функцию можно показать и проверить на экране.
   Любой новый SQL (репозиторий, агрегат, снимок для карты) дополнительно проверяется интеграционным
   тестом на настоящей Postgres (`*.int.test.ts`, `pnpm test:integration`, образец
   `modules/sensors/sensors.int.test.ts` в бэкенде).
6. **Данные настоящие, а выводы честные.** Тестовая база заполняется **синтетикой** (`pnpm db:seed`).
   Результаты экспериментов для диплома получают только на реальных данных (выгрузку даёт владелец,
   сервер вам не нужен). Синтетические графики в диплом идут с подписью «синтетические данные».
7. **Маленькие PR.** Один PR — одна задача, не больше ~400 строк кода без учёта тестов. Ветка от
   свежего `main`; **после слияния PR старую ветку не продолжают**, новая ветка от нового `main`
   (иначе GitHub откроет повторный PR с уже влитыми коммитами).

## 4. Как мы работаем

1. Один раз: запусти проект по `README.md` (две команды: бэкенд и фронтенд). Не получилось, пиши, а
   не мучайся: это ошибка в инструкции, её надо исправить.
2. Каждое задание — **отдельная ветка** и **отдельный pull request**. Названия: `feature/...`
   (`feature/map-page`, `feature/stations-model`, `feature/quality-gaps`).
3. В описании PR своими словами: что сделал, зачем, как проверить. Шаблон подскажет. Если
   правилась форма данных, пометь это: фронтенд и бэкенд должны остаться согласованными.
4. Перед PR запусти проверки и посмотри результат глазами.
   * Бэкенд: `pnpm typecheck`, `pnpm test`.
   * Фронтенд: `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm build`; в браузере консоль без
     ошибок, светлая и тёмная темы, ширины 1440 и 375 px, три языка.
   CI запускает те же команды; для влития нужны зелёный CI и одно одобрение владельца.
5. На ревью я могу спросить про любую строку: ты обязан уметь её объяснить. Это нужно и для защиты.
6. С `main` напрямую работать нельзя. Доступа к боевому серверу нет и не будет: выкатывает владелец.

### ИИ-помощник (обязательные правила)

* Дай ему **вступление** ниже, текст задания и конкретные файлы, с которыми работаешь. Не проси
  «сделай карту» или «сделай аналитику»: проси маленькими шагами по заданию.
* Проси **объяснять**, а не только писать. Код, который ты не понимаешь, на защите не поможет.
* Проверяй сам: запусти, посмотри, прогони тесты. ИИ часто пишет код, который выглядит правильно,
  но не работает или нарушает архитектуру.
* Тесты запускаются в Node, без браузера: логику пиши чистыми функциями.
* Фронтенд на Tailwind v4: настройки в `src/app/styles/globals.css`, файла `tailwind.config.ts` нет.

**Вступление для ИИ-помощника** (скопируй в начало разговора):

> Ты работаешь в проекте Weather NUU: бэкенд `weather-backend` (Node 20, Fastify, Drizzle,
> PostgreSQL, Zod, pnpm/turbo) и фронтенд `weather-nuu` (React 19, TypeScript, Vite, Tailwind v4,
> Feature-Sliced Design, ECharts, i18next ru/uz/en). Прочитай `AGENTS.md`, `CONTRIBUTING.md` и
> `docs/ARCHITECTURE.md` обоих репозиториев и файл `docs/tasks/<мой документ>.md`, моё задание
> `<номер>`. Правила: правь только каталоги моей зоны (таблица в `docs/tasks/README.md`);
> форма API только через `@weather/contracts`; шкалы AQI только через `@weather/air-quality`
> (бэкенд) и `src/shared/lib/air-quality` (фронтенд), не пиши свою; расчёты чистыми функциями с
> тестами Vitest рядом; тексты интерфейса только через i18n во всех трёх языках, в свой
> файл-пространство имён; слой `shared` не импортирует из верхних слоёв; никаких секретов в коде;

> код маленькими шагами и объясняй каждый.
