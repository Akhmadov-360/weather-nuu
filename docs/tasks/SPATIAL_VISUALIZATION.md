# Задания: пространственная визуализация и серверная часть карты (Тулешов Т.)

Тема: «Web-платформа агрегации и пространственной визуализации экологических показателей
городского воздуха». Твоя зона — **весь путь данных для карты**: от станции и внешнего источника в
базе, через расчёт AQI и API, до карты и тепловой интерполяции в браузере. Это сквозная работа
(бэкенд + фронтенд), поэтому у неё есть и серверное, и визуальное ядро для защиты.

Сначала прочитай [README.md](README.md) в этой папке: там правила работы, зоны каталогов, как не
мешать другим и вступление для ИИ-помощника. Это задание не повторяет их.

> Статус (обновлено 13.10.2026): все задания можно начинать сразу: контракт фиксируется первым
> PR (B1), дальше сервер и карта идут параллельно по общим фикстурам. Подготовку делает владелец
> (P1–P5 в README): пакет `@weather/air-quality`, пакет `@weather/timeseries`, пространства имён
> переводов, расширенные тестовые данные.

## Что уже есть и что пригодится

* Шкалы AQI (US EPA, редакция 2024) и цвета категорий: `src/shared/lib/air-quality/`; цвета
  `--aqi-*` в `globals.css` для обеих тем; образец оформления: `widgets/weather-summary/ui/AirQualityCard.tsx`.
* Живая пыль собственной станции Room (с 10.10.2026), сбой датчика сохраняется как `null`.
* Агрегаты истории (`GET /v1/sensors/:source/aggregate`, `resolveAutoBucket`), keyset-пагинация,
  потоковая выгрузка, фоновая задача (`jobs/hourly-snapshot.ts`) как образец планировщика.
* Клиент Open-Meteo на фронтенде (`entities/atmosphere/api/open-meteo.ts`): показывает, как мы
  ходим во внешний API без ключа (кэш, таймауты).

## Честно о данных

* У нас две собственные станции (Room, Street) **в одном здании**. Интерполировать между ними
  бессмысленно: карта получает смысл, только когда есть внешние станции вокруг. Поэтому адаптер
  внешнего источника (B6) — не бонус, а условие того, что карта вообще что-то показывает.
* Пыль есть только у Room, а официальный AQI считается по суткам: смотри подписи «за 10 мин» и
  «за 24 ч» в карточках, у карты та же логика (поле `aqiBasis`).
* Данные модели (прогноз реанализа) и измерения станции — разные вещи; в контракте это поле
  `provenance`, в попапе карты это подписано.

## Контракт данных (черновик, уточняется в B1)

Читай данные через один модуль (`entities/station`), не размазывай по компонентам.

```jsonc
// Станция
{
  "id": "room", "name": "Аудитория", "type": "own",       // own | external
  "provenance": "measured",                               // measured | modelled
  "lat": 41.30, "lon": 69.24,
  "attribution": null                                     // для внешних: строка источника/лицензии
}

// Снимок для карты: последние значения всех станций
{
  "generatedAt": "2026-10-10T12:00:00.000Z",
  "items": [
    {
      "stationId": "room",
      "pm25": 18, "pm10": 30, "temp": 24.1, "hum": 38,
      "aqi": 64, "aqiCategory": "moderate",
      "aqiBasis": "24h",                                  // 24h | 10min | hourly | null
      "measuredAt": "2026-10-10T11:59:50.000Z"
    }
  ]
}
```

* `aqiCategory`: `good` · `moderate` · `unhealthy_sensitive` · `unhealthy` · `very_unhealthy` ·
  `hazardous` (US EPA AQI: 0–50, 51–100, 101–150, 151–200, 201–300, 301+).
* Любое числовое поле может быть `null`: `null` значит «нет показания» и **никогда не ноль**.
  У Street датчика пыли нет вообще (в интерфейсе: «Датчик не установлен»), у Room он есть, но
  может молчать («Нет показаний пыли»). В попапе различай эти случаи подписью.
* Официальный US EPA AQI считается по 24-часовому среднему; `aqiBasis` говорит, по чему посчитано
  на самом деле. Координаты в фикстурах **демонстрационные**, настоящие уточним позже.
* Фронтенд хранит копию фикстур (`src/entities/station/fixtures/`), бэкенд — оригинал
  (`packages/contracts/fixtures/`). Меняешь форму: обновляешь оба и пишешь об этом в PR.

## B2. Модель станций в базе и `GET /v1/stations`

**Что сделать:**
1. Короткая **запись решения** `docs/decisions/0001-stations-model.md` (в бэкенде): как хранить

   `is_active`) и отдельная таблица `station_readings` (`station_id`, `measured_at`, `pm25`,
   `pm10`, `no2`, `o3`, `temp`, `hum`, уникальность `(station_id, measured_at)`, индекс по ним же).
   Таблицу `sensor_data` **не меняй**: прошивка пишет в неё, формат трогать нельзя. Объясни, почему

2. Схема в `db/schema.ts`, миграция (`pnpm db:generate`, проверь SQL глазами, миграции только
   добавляют), заполнение: станции `room` и `street` (координаты демонстрационные, вынеси в
   конфигурацию), повторный запуск не создаёт дубликатов.
3. Модуль `modules/stations` (routes → service → repo): `GET /v1/stations`, ответ по `StationListSchema`.

**Готово, когда:** `curl localhost:8002/v1/stations` отдаёт станции по контракту; есть интеграционный тест (`*.int.test.ts`: миграция, повторное заполнение без дублей, ответ по схеме); миграция
применяется на чистой базе и на существующей; `sensor_data` не изменилась; `pnpm typecheck` и
`pnpm test` зелёные.

**Что изучишь:** проектирование схемы БД, индексы, миграции Drizzle, обратная совместимость.
**Для диплома:** ER-диаграмма и текст записи решения (обоснование схемы — готовый абзац раздела
«Проектирование базы данных»).

## B3. Серверный расчёт AQI

**Цель:** сервер считает AQI тем же способом, что и фронтенд, и говорит, по какому периоду.

**Что сделать:** чистая функция `computeAqi(input)` в `modules/map/` на основе
`@weather/air-quality` (его даёт владелец, P1). Правила: для собственной станции с пылевым
датчиком берётся среднее PM2.5 за 24 часа, если покрытие суток не менее 75% (`aqiBasis: "24h"`),
иначе среднее за 10 минут при покрытии не менее 50% (`"10min"`); для внешних источников значение
из источника (`"hourly"`); нет данных: `aqi: null`, `aqiBasis: null`. Концентрация усекается до
разряда стандарта (так делает EPA и так уже сделано во фронтенде), не округляется. Определяющий
загрязнитель — тот, у которого индекс выше (PM2.5 или PM10).
Тесты: общий файл эталонных значений `aqi-vectors.json` (даёт владелец, P1) проходит в обоих
репозиториях; плюс граничные значения категорий, `null`, покрытие ровно 75% и 74%.

**Готово, когда:** тесты проходят, результат совпадает с карточкой Room на фронтенде для одного
и того же момента (сравни вручную и приложи скриншот в PR).

**Что изучишь:** как считают индекс качества воздуха, зачем нужны усреднение и покрытие,
тестирование численной логики.
**Для диплома:** раздел «Расчёт AQI»: формула, периоды, обработка нехватки данных, ограничения.
**Бонус:** NowCast (взвешенное среднее за 12 часов, официальный способ для «почти реального»
времени у EPA): сравнить с 24-часовым и 10-минутным.

## B4. Снимок для карты: `GET /v1/map/snapshot`

**Цель:** один быстрый запрос отдаёт последние значения всех станций.

**Что сделать:** модуль `modules/map`. Параметр `at` (ISO-время, необязательный; по умолчанию
сейчас): берётся последнее измерение не позже `at` и не старше допустимого окна (по умолчанию 2 часа),
иначе у станции `null` значения. Запрос к БД **без N+1** (один запрос на тип источника;
`DISTINCT ON` или боковое соединение), проверка `EXPLAIN` на использование индекса. Сборка
снимка из строк — чистая функция с тестами: станция без данных; устаревшее измерение; `at` в
прошлом; `null` в полях.

**Готово, когда:** ответ проходит `MapSnapshotSchema`, а интеграционный тест на настоящей Postgres проверяет случаи «нет данных», `at` в прошлом и устаревшее измерение; на сидированной базе (90 дней) время
ответа замерено (серия из 100 запросов, медиана и p95 записаны в PR); тесты проходят.

**Что изучишь:** оптимизация запросов, индексы, чтение плана запроса.
**Для диплома:** таблица замеров «до/после» индекса или варианта запроса.

## B5. История станции: `GET /v1/stations/:id/history`

**Цель:** мини-график в попапе станции и слайдер времени работают и для внешних станций.

**Что сделать:** параметры `from`, `to`, `bucket=auto`; для собственных станций используй готовый
агрегатный репозиторий (`resolveAutoBucket`, не пиши второй), для внешних запрос к
`station_readings` с теми же корзинами; форма ответа как у существующего агрегата, где это
возможно (переиспользуй схему из `contracts`).

**Готово, когда:** график строится по обоим типам станций; тесты на выбор корзины для разных
диапазонов; диапазон длиннее допустимого отвергается понятной ошибкой.

## B6. Адаптер внешнего источника (агрегация данных)

**Цель:** в системе появляются внешние станции с PM2.5/PM10, это и есть «агрегация» из темы диплома.

**Что сделать:**
1. **Выбор источника.** Короткая записка (1 страница) `docs/decisions/0002-external-source.md`:
   сравни 2–3 открытых источника. Кандидаты (проверь актуальные условия сам, мы их не
   проверяли): Open-Meteo Air Quality (по нашим сведениям, без ключа, но это **модельные**
   значения на сетке, не измерения), OpenAQ (реальные станции, по нашим сведениям нужен
   бесплатный ключ, проверь покрытие Ташкента), другие агрегаторы. Критерии: покрытие города,
   тип данных (измерение или модель), лицензия и требование указывать источник, лимиты, ключ,
   стабильность. Вывод и обоснование записать. Без обсуждения с владельцем источник не выбирай.
2. **Интерфейс адаптера** в `modules/sources/`: `SourceAdapter { id; fetchLatest(signal): Promise<NormalizedReading[]> }`
   и нормализация в общий формат (`pm25`, `pm10`, `measuredAt`, `stationKey`, единицы µg/m³).
   Адаптер ничего не знает о Fastify и БД: он получает ответ внешнего API и отдаёт нормализованный
   массив. Запись в БД через `service`.
3. **Планировщик:** фоновая задача по образцу `jobs/hourly-snapshot.ts`: период из конфигурации,
   запуски не накладываются, таймаут запроса, ошибка источника пишется в лог и **не роняет API**.
4. **Станции:** внешние станции создаются повторяемо (upsert) с координатами и `attribution`.
5. **Секреты и сеть:** ключи только в переменных окружения (добавь необязательные поля в `env.ts`
   и `.env.example`), в git ключей нет; в тестах сетевых запросов нет: ответы записаны в файлы-
   фикстуры. Уважай лимиты источника.

**Готово, когда:** после запуска `GET /v1/stations` содержит не менее 5 внешних станций вокруг
Ташкента, снимок отдаёт их PM2.5; при недоступном источнике API здоров (`/v1/health`), в логе
понятная ошибка; тесты адаптера и нормализации на записанных ответах проходят; в попапе карты
видно `attribution`.

**Что изучишь:** интеграции с внешними API, нормализация данных, надёжность фоновых задач.
**Для диплома:** диаграмма потока данных, таблица сравнения источников, описание нормализации,
честное «что делать, если источник упал».
**Бонус:** сверка Room с ближайшей внешней станцией (разность PM2.5 за период, график): прямой
вклад в раздел о валидации; второй источник.

## T4. Алгоритм интерполяции IDW (ядро визуальной части)

**Цель:** по значениям в нескольких станциях оценить значение в любой точке города.

**Идея:** метод обратных взвешенных расстояний (IDW). Значение в точке `x`:
`v(x) = Σ wᵢ·vᵢ / Σ wᵢ`, где `wᵢ = 1 / dᵢᵖ`, `dᵢ` — расстояние до станции `i`, `p` — степень
(обычно 2). Если точка совпала со станцией, берём её значение.

**Что сделать:** чистая функция без интерфейса `src/shared/lib/geo/idw.ts` (+ расстояние между
координатами, формула гаверсинусов). Слой `shared` не импортирует из `entities`, `features`,
`widgets` (проверяет ESLint), поэтому функция принимает простые числа и координаты, а не типы станций.
Тесты: одна станция; две станции (середина между ними); совпадение точки со станцией; станции
без данных (`null`) пропускаются; влияние степени `p`; пустой список; станции из внешних
источников с `provenance: "modelled"` по умолчанию можно исключить (параметр).

**Готово, когда:** тесты проходят; в `docs/` короткое описание алгоритма своими словами.
**Что изучишь:** пространственная интерполяция и её ограничения (мало точек: это оценка, а не
измерение), тестирование численных функций.

## T5. Тепловая карта

**Цель:** цветовое поле поверх карты, построенное по IDW.

**Что сделать:** слой на `canvas` поверх карты: сетка точек, значение по IDW в каждой, цвет по
шкале AQI; регулятор прозрачности; ограничение дальности (далеко от любой станции поле
бледнеет: там мы ничего не знаем); пересчёт только при движении и масштабе, не на каждый кадр.
На слое подпись «интерполяция, оценка по N станциям».

**Готово, когда:** на фикстуре плавная заливка, карта не тормозит при перемещении.
**Что изучишь:** canvas, производительность отрисовки, компромисс «разрешение сетки ↔ скорость».
**Для диплома:** измерь время построения при разных разрешениях и запиши в таблицу.

## T6. Подключение к настоящему API

**Цель:** заменить фикстуры на запросы к серверу (теперь он твой, B2–B4).

**Что сделать:** запросы через React Query (по образцу `entities/weather/api`), состояния
загрузки, ошибки и «нет данных», автообновление. Новые пути добавь в dev-прокси (`vite.config.ts`);
настройки nginx на сервере сделает владелец, пришли ему нужные пути в описании PR.

**Зависит от:** B2 и B4 (твои же). До них карта живёт на фикстурах.

## T7. Слайдер времени

**Цель:** посмотреть, как выглядел воздух в прошлом.

**Что сделать:** слайдер выбора момента; карта и поле перерисовываются по снимку на этот момент
(`GET /v1/map/snapshot?at=`); кнопка «вернуться к текущему»; пока идёт перетаскивание, запросы
не сыплются (отложенная отправка).

**Зависит от:** B4 с параметром `at` и, для попапа, B5.

## T8. Переключатель показателей, телефон, языки

**Что сделать:** выбор показателя (PM2.5, PM10, температура, влажность) с подходящей шкалой и
легендой; адаптивная вёрстка (карта удобна на телефоне); проверка всех текстов на ru/uz/en;
скриншоты «до/после» в описании PR.

## T9. Исследовательская часть (для текста диплома)

Это не код, но по сути половина защиты.

1. **Сравнение с аналогами** (например, IQAir, PurpleAir, OpenAQ): таблица «что умеет каждый /
   чего нет у нас / чем наша платформа отличается», скриншоты, выводы.
2. **Эксперименты с IDW:** как меняется картина при разных значениях `p` и разрешении сетки;
   где метод ошибается (края, мало станций). Графики и скриншоты с подписями. Желательно:
   **перекрёстная проверка** (по очереди убирай одну станцию и оцени её значение по остальным:
   средняя ошибка покажет, насколько интерполяции можно верить).
3. **Ограничения:** честно описать, чего карта не может (мало точек, нет калибровки датчиков).
   Уже записано в `docs/PROJECT_REPORT.md` (разделы 11.4 и 13): Plantower завышает показания
   при высокой влажности, MQ-датчики дают оценки, региональные нормы не подтверждены (используется
   US EPA), 10-минутное среднее не равно официальному суточному AQI.

# Что вынести в диплом

Защита индивидуальная: комиссия спросит, что сделано **лично тобой**. У тебя два ядра: серверное
(данные и расчёт) и визуальное (карта и интерполяция). Платформа (приём данных с датчиков,
дашборд, выкатка), шкалы AQI во фронтенде и аналитический слой группы №7 в дипломе описываются как
«использованная система»: ссылайся на них, но не заявляй как своё. Авторство подтверждает история
pull request под твоим именем.

**Твой вклад одной фразой:** модель агрегации разнородных источников данных о воздухе в единую
систему станций и её пространственная визуализация на карте с интерполяцией.
