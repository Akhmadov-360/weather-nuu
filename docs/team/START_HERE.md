Прочитайте этот файл один раз от начала до конца, потом возвращайтесь к нужным разделам. Здесь всё,
что нужно для работы: что установить, как скачать проект, как его запустить, как работать с Git,
как пользоваться Docker и pnpm, как открыть pull request и что делать, когда что-то сломалось.
Предполагается, что вы **никогда этого не делали**: непонятные слова объяснены сразу.

Если что-то не получилось, это нормально. Не мучайтесь больше 20–30 минут: напишите владельцу
проекта (Ахмадову А.), приложите скриншот и текст ошибки. Часто это недочёт инструкции, и тогда мы её
исправим.

## 1. Словарь

| Слово | Простыми словами |
|-------|------------------|
| **Репозиторий** (репо) | папка проекта, в которой хранится вся история изменений. У нас два: `weather-nuu` (то, что видит пользователь) и `weather-backend` (серверная часть, база данных) |
| **GitHub** | сайт, где лежат репозитории и где проверяют работу друг друга |
| **Git** | программа на вашем компьютере, которая запоминает изменения файлов и отправляет их на GitHub |
| **Клонировать** | скачать репозиторий с GitHub на свой компьютер |
| **Ветка** (branch) | ваша личная копия проекта, где вы делаете задание, не мешая другим. Главная ветка называется `main`, туда напрямую писать нельзя |
| **Коммит** (commit) | сохранённый шаг работы с короткой подписью «что сделал» |
| **Push** | отправить свои коммиты на GitHub |
| **Pull request** (PR) | заявка «посмотрите и добавьте мои изменения в `main`» |
| **CI** | автоматическая проверка, которая запускается на GitHub для каждого PR (типы, тесты, сборка). Должна быть зелёной |
| **Ревью** | проверка вашего PR человеком; владелец может задать вопросы по любой строке |
| **Node.js** | среда, в которой запускается наш код (нужна версия 20) |
| **pnpm** | менеджер пакетов: скачивает нужные библиотеки (`pnpm install`) и запускает команды проекта |
| **Docker** | программа, которая запускает базу данных и сервер в изолированных «контейнерах», чтобы ничего не устанавливать вручную |
| **Контейнер** | запущенная изолированная программа внутри Docker (например, база данных) |
| **Терминал** | окно, куда вводят команды текстом |

## 2. Что установить

Работает Windows 10 или 11; на macOS и Linux всё то же, отличается только установка и пара команд
(отмечено ниже).

1. **Git**: https://git-scm.com (на Windows ставится вместе с программой «Git Bash»). При установке
   можно оставлять всё по умолчанию.
2. **Node.js 20 (LTS)**: https://nodejs.org (скачайте версию 20 LTS). После установки **закройте и
   заново откройте терминал**.
3. **Docker Desktop**: https://www.docker.com/products/docker-desktop. Подробности в разделе 5.
4. **Редактор кода**: Visual Studio Code, https://code.visualstudio.com. Расширения: «ESLint»; по желанию
   «GitLens» и «Docker».
5. **pnpm** (менеджер пакетов). В терминале выполните:

   ```bash
   corepack enable
   ```

   Если команда выдала ошибку про права доступа, откройте терминал **от имени администратора** (на Windows:
   правой кнопкой по PowerShell, «Запуск от имени администратора») и повторите. Запасной вариант:
   `npm install -g pnpm`.

Проверка, что всё стоит (каждая команда должна напечатать номер версии, а не ошибку):

```bash
git --version
node --version     # должно быть v20.x.x или выше
pnpm --version
docker --version
```

> **Какой терминал использовать на Windows.** Самый простой: открыть папку проекта в VS Code и нажать
> `Ctrl+` ` (обратная кавычка), откроется встроенный терминал. Команды в этой инструкции работают в
> Git Bash и в PowerShell; там, где они отличаются, это указано.

## 3. Доступ к репозиториям и настройка Git

1. Владелец пригласит вас в оба репозитория. На вашу почту придёт письмо от GitHub: нажмите **Accept
   invitation** (принять приглашение). Если вы не зарегистрированы на GitHub, зарегистрируйтесь на
   https://github.com и сообщите владельцу своё имя пользователя.
2. Один раз сообщите Git, кто вы. Имя и почта попадут в подписи ваших коммитов (по ним видно, кто что
   сделал, это нужно и для защиты диплома). Используйте имя и почту вашего аккаунта GitHub:

   ```bash
   git config --global user.name "Ваше Имя Фамилия"
   git config --global user.email "ваша-почта@example.com"
   ```

   Если не хотите показывать настоящую почту, GitHub даёт скрытый адрес вида
   `12345+имя@users.noreply.github.com` (Settings, Emails).
3. Чтобы Git не открывал непонятный текстовый редактор Vim, когда ему нужна подпись, выполните:

   ```bash
   git config --global core.editor "code --wait"
   ```

   (нужен установленный VS Code; если вдруг оказались в Vim, выход: нажмите `Esc`, наберите `:q!` и Enter).
4. При первом `git clone` или `git push` откроется окно входа в GitHub: войдите, дальше Windows запомнит
   вход. Пароль от аккаунта никому не передавайте.

## 4. Скачать проекты

Создайте папку, где будут лежать оба проекта **рядом**, например `C:\diploma`. Откройте терминал в этой
папке и выполните:

```bash
git clone https://github.com/Akhmadov-360/weather-nuu.git
git clone https://github.com/Akhmadov-360/weather-nuu-backend.git weather-backend
```

Получится так:

```
C:\diploma\
  weather-nuu\        фронтенд (то, что видит пользователь)
  weather-backend\    бэкенд (сервер и база данных)
```

(Название папки `weather-backend` мы задали в конце второй команды: так привыкли в документах.)

Дальше: откройте VS Code, меню File, Open Folder и выберите нужный проект. Рекомендуем держать два окна
VS Code, по одному на репозиторий.

**Что читать после установки:** [README.md](README.md) этой папки (правила и зоны), `docs/ARCHITECTURE.md`
в обоих репозиториях, файл с вашими заданиями ([SPATIAL_VISUALIZATION.md](SPATIAL_VISUALIZATION.md) или
[ANALYTICS.md](ANALYTICS.md)) и [SUMMARY.md](SUMMARY.md): все задания простыми словами.

## 5. Docker: что делать после установки

Docker нужен, чтобы запустить **базу данных и сервер** одной командой. Устанавливать PostgreSQL вручную
не нужно.

### 5.1 Установка и первый запуск

1. Скачайте и установите Docker Desktop. Установщик на Windows сам предложит включить WSL 2; согласитесь и,
   если попросит, перезагрузите компьютер.
2. Запустите программу **Docker Desktop** (значок кита). Дождитесь, пока в левом нижнем углу окна
   появится зелёный индикатор **Engine running**. Пока он не зелёный, команды `docker` не работают.
3. Если пишет про виртуализацию или «WSL 2 installation is incomplete»: включите виртуализацию в BIOS
   (параметр называется Intel VT-x, AMD-V или SVM Mode) и установите обновление WSL: в PowerShell от
   администратора `wsl --update`, затем перезагрузка.
4. Проверка (в терминале):

   ```bash
   docker --version
   docker compose version
   docker run --rm hello-world
   ```

   Последняя команда скачивает крошечную программу и печатает приветствие «Hello from Docker!». Если
   увидели, всё работает.
5. Рекомендуется выделить Docker хотя бы 4 ГБ памяти: Docker Desktop, значок шестерёнки, Resources.

### 5.2 Команды Docker, которые вам понадобятся

Все команды запускаются **в папке `weather-backend`**.

| Что нужно | Команда |
|-----------|---------|
| Запустить базу, сервер и «фейковые датчики» (**основной вариант**) | `docker compose -f docker-compose.dev.yml --profile live up --build` |
| То же без фейковых датчиков (будут только старые тестовые данные) | `docker compose -f docker-compose.dev.yml up --build` |
| Запустить только базу данных (для тестов и запуска сервера вручную) | `docker compose -f docker-compose.dev.yml up -d db` |
| Остановить (сначала `Ctrl+C` в окне, где идёт запуск) | `docker compose -f docker-compose.dev.yml down` |
| Остановить и **стереть базу** (начать с нуля) | `docker compose -f docker-compose.dev.yml down -v` |
| Посмотреть запущенное | `docker ps` |
| Читать журнал сервера (выход `Ctrl+C`) | `docker compose -f docker-compose.dev.yml logs -f api` |

Те же команды есть в коротком виде: `pnpm stack:live`, `pnpm stack:up`, `pnpm stack:down`,
`pnpm stack:reset` (запускать в `weather-backend` после `pnpm install`).

**Первый запуск долгий** (несколько минут): Docker скачивает образы и собирает сервер. Следующие запуски
быстрые. Успешный запуск выглядит так: в окне идёт журнал, а по адресу http://localhost:8002/v1/health
в браузере появляется `{"status":"ok","db":"ok"}`.

**Если порт занят** («port is already allocated»): другой программе принадлежит порт. Освободите его или
задайте другой: в PowerShell `$env:DB_PORT=55440; docker compose -f docker-compose.dev.yml up --build`
(для API вместо `DB_PORT` переменная `API_PORT`); в Git Bash `DB_PORT=55440 docker compose ...`.
Если меняли порт API, сообщите об этом фронтенду (см. 6.2).

**Чтобы освободить место на диске** иногда помогает `docker system prune` (удаляет остановленные
контейнеры и неиспользуемые образы). Перед ней убедитесь, что не потеряете нужное; ваши данные проекта в
репозитории она не трогает.

## 6. Запуск проекта

Проект состоит из двух частей, и для работы нужны **обе запущенными**. Понадобятся два терминала.

### 6.1 Серверная часть (бэкенд)

Терминал 1, папка `weather-backend`: команда запуска из раздела 5.2 (с `--profile live`). Окно оставьте
открытым, пока работаете. Что запустилось:

* база данных PostgreSQL (порт 55432) с тестовыми данными за 90 дней;
* сервер API на порту **8002**;
* «фейковые датчики»: они шлют показания раз в 5 секунд, поэтому на дашборде горит LIVE.

### 6.2 Фронтенд

Терминал 2, папка `weather-nuu`:

```bash
pnpm install     # один раз и после изменения зависимостей: скачать библиотеки
pnpm dev         # запустить сайт для разработки
```

Откройте в браузере http://localhost:5173. Вы увидите дашборд с данными. Изменили файл, сохранили,
страница обновилась сама. Остановить: `Ctrl+C` в окне терминала.

Если бэкенд работает на другом порту, перед `pnpm dev` задайте адрес: PowerShell
`$env:API_PROXY_TARGET="http://localhost:8010"`; Git Bash `API_PROXY_TARGET=http://localhost:8010 pnpm dev`.

Особые режимы просмотра для разработки (работают только при `pnpm dev`): добавьте к адресу `/room?time=18:20`
(время суток), `?conn=archive` (состояние «архив»), `?date=2026-12-31` (праздник), `?weather=rain`
(погода), `?level=full|calm|off` (уровень анимации).

### 6.3 Если вы правите код бэкенда без Docker для сервера

Тогда в Docker запускается только база, а сервер запускается из кода на вашем компьютере (это удобнее,
код перезагружается при сохранении). Папка `weather-backend`:

```bash
pnpm install
docker compose -f docker-compose.dev.yml up -d db     # только база
cp apps/api/.env.example apps/api/.env                # PowerShell: Copy-Item apps/api/.env.example apps/api/.env
pnpm db:migrate                                       # создать таблицы
pnpm db:seed                                          # тестовые данные
pnpm dev                                              # сервер на :8002 с перезапуском при сохранении
pnpm sim                                              # (в другом терминале) фейковые датчики
```

Файл `apps/api/.env` содержит только локальные значения и в Git не попадает. Настоящие пароли и ключи
в репозиторий **никогда** не кладём.

## 7. Команды pnpm

`pnpm` запускает команды из файла `package.json` проекта. Все команды выполняются **в папке нужного
репозитория**. Если вы что-то установили или поменяли ветку и всё «сломалось», сначала выполните
`pnpm install`.

### Фронтенд (`weather-nuu`)

| Команда | Что делает |
|---------|-----------|
| `pnpm install` | скачать библиотеки (один раз, потом после смены ветки или обновления проекта) |
| `pnpm dev` | запустить сайт для разработки, http://localhost:5173 |
| `pnpm typecheck` | проверить типы TypeScript (находит опечатки и несовпадения данных) |
| `pnpm lint` | проверить стиль и ошибки кода (**0 ошибок обязательно**; два предупреждения о «Fast refresh» старые и нормальны) |
| `pnpm test` | запустить автоматические тесты |
| `pnpm test:watch` | тесты в режиме наблюдения (перезапускаются при сохранении) |
| `pnpm build` | проверка типов и сборка боевой версии (медленнее остальных) |
| `pnpm preview` | посмотреть собранную версию |

**Перед каждым PR запустите по порядку:** `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm build`. Все
четыре должны пройти. Те же четыре запускает CI на GitHub.

### Бэкенд (`weather-backend`)

| Команда | Что делает |
|---------|-----------|
| `pnpm install` | скачать библиотеки |
| `pnpm typecheck` | проверка типов |
| `pnpm test` | модульные тесты (быстрые, без базы) |
| `pnpm test:integration` | интеграционные тесты на настоящей базе (нужен запущенный `docker compose ... up -d db`); **обязательны, если меняли SQL или маршруты** |
| `pnpm dev` | запустить сервер для разработки (см. 6.3) |
| `pnpm db:migrate` | применить миграции базы данных |
| `pnpm db:generate` | создать миграцию после правки схемы (`schema.ts`); миграции делает только владелец зоны станций |
| `pnpm db:seed` | заполнить базу тестовыми данными за 90 дней |
| `pnpm db:seed --force` | стереть таблицу и заполнить заново |
| `pnpm db:seed --anomalies` | то же, но с известными «дефектами» для проверки алгоритмов (список в `apps/api/seed-anomalies.manifest.json`) |
| `pnpm sim` | фейковые датчики (шлют показания раз в 5 секунд в локальный сервер) |
| `pnpm --filter @weather/air-quality test` | тесты одного пакета (пример: пакета шкал AQI) |

**Перед каждым PR запустите:** `pnpm typecheck`, `pnpm test` и, если меняли SQL или маршруты,
`pnpm test:integration`.

Команды `db:seed` и `sim` **отказываются работать с чужой базой** (только localhost): случайно испортить
боевые данные невозможно.

### Чего не делать с pnpm

* Не запускайте `npm install`: в проекте только `pnpm` (иначе появятся лишние файлы).
* Не добавляйте новые библиотеки без согласования с владельцем проекта; если очень нужно, спросите.
* Не удаляйте `pnpm-lock.yaml` и не правьте его вручную.

## 8. Git: ежедневная работа

### 8.1 Главная идея

`main` всегда должна работать, поэтому в неё **никто не пишет напрямую**. Каждое задание делается в
своей **ветке** и попадает в `main` только через pull request после проверки. Одно задание, одна ветка,
один PR.

### 8.2 Цикл работы над заданием (шпаргалка)

```bash
# 1. Всегда начинаем со свежего main
git checkout main
git pull

# 2. Создаём ветку под задание (название: feature/что-делаем)
git checkout -b feature/map-page

# 3. Работаем: правим файлы, запускаем проверки (pnpm typecheck, test ...)

# 4. Смотрим, что изменилось
git status
git diff

# 5. Сохраняем шаг (коммит)
git add .
git commit -m "feat: add map page with station markers"

# 6. Отправляем на GitHub
git push -u origin feature/map-page
```

После `git push` GitHub напечатает ссылку для создания pull request (см. раздел 9). В следующие разы
достаточно `git push` без `-u origin ...`.

### 8.3 Что означает каждая команда

| Команда | Что делает |
|---------|-----------|
| `git status` | показывает, какие файлы изменены и на какой вы ветке; **смотрите её перед каждым коммитом** |
| `git diff` | показывает построчно, что вы изменили |
| `git add <файл>` | отмечает файл для следующего коммита; `git add .` отмечает всё изменённое |
| `git commit -m "текст"` | сохраняет отмеченное как шаг с подписью |
| `git push` | отправляет коммиты на GitHub |
| `git pull` | скачивает свежие изменения с GitHub в текущую ветку |
| `git checkout <ветка>` | переключиться на ветку |
| `git checkout -b <имя>` | создать новую ветку и сразу переключиться на неё |
| `git branch` | список веток (звёздочка у текущей) |
| `git log --oneline -10` | последние 10 коммитов |
| `git fetch` | узнать о новостях на GitHub, ничего не меняя у вас |

### 8.4 Названия веток и подписи коммитов

* **Ветка:** `feature/что-делаем` (новая возможность), `fix/что-чиним`, `docs/что-пишем`, `chore/мелочь`.
  Латиницей и через дефис: `feature/map-page`, `feature/idw`, `fix/chart-zoom`.
* **Подпись коммита:** коротко, по делу, в начале тип: `feat:` (новое), `fix:` (исправление), `test:`
  (тесты), `docs:` (документы), `chore:` (прочее). Пример: `fix: show gap in the chart for missing dust`.
  Одна мысль на коммит; коммитов в ветке может быть сколько угодно, при слиянии они склеятся в один.
* Описание шага «что и зачем» своими словами нужно в PR, а не в подписи коммита.

### 8.5 Перед коммитом проверьте

1. `git status`: нет ли среди файлов чего-то лишнего (`.env`, пароли, скриншоты с личными данными)?
2. Вы в **своей ветке**, а не в `main` (в `git status` первая строка `On branch feature/...`)?
3. Запускались `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm build` (фронтенд) или `typecheck`, `test`
   (бэкенд)?

Если случайно закоммитили секрет (пароль, ключ), **сразу сообщите владельцу**: не пытайтесь убрать
самостоятельно, ключ придётся заменить.

### 8.6 Обновить свою ветку свежим main

Пока вы работаете, другие добавляют свои изменения в `main`. Чтобы ваш PR можно было влить, ветка должна
быть актуальной. Раз в день или перед PR:

```bash
git fetch
git merge origin/main
```

Если Git сообщил «Already up to date», всё хорошо. Если написал про **конфликт**, перейдите к
разделу 10. После слияния снова запустите проверки и сделайте `git push`.

### 8.6.1 После слияния вашего PR

Когда владелец влил PR, **старую ветку не продолжают**. Для следующего задания:

```bash
git checkout main
git pull
git branch -d feature/map-page          # удалить старую ветку у себя (необязательно)
git checkout -b feature/idw             # новая ветка от свежего main
```

(Если продолжить старую ветку, GitHub откроет повторный PR с уже влитыми коммитами. Мы уже наступали на
эти грабли.)

## 9. Pull request

После `git push` откройте страницу репозитория на GitHub. Появится жёлтая полоса **Compare & pull
request**; нажмите её (или Pull requests, New pull request, ваша ветка). Заполните шаблон:

1. **Что изменено и зачем**: 2–4 предложения своими словами. Вы должны уметь объяснить каждую строку.
2. **Задание и зона**: например, `T3`, `B2`, `A1`, `F0` и ваша зона (карта, аналитика).
3. **Как проверить**: какие шаги вы выполнили; для изменений интерфейса приложите **скриншоты** (светлая и
   тёмная тема).
4. **Чек-лист**: отметьте галочками только то, что сделали на самом деле.

Дальше:

* Подождите проверки CI (1–5 минут): внизу страницы PR появятся пункты. Все должны стать **зелёными**.
  Красный: нажмите **Details**, прочитайте журнал, воспроизведите ошибку у себя той же командой (например,
  `pnpm test`), исправьте, сделайте новый коммит и `git push`: PR обновится сам.
* Владелец проекта посмотрит PR и оставит комментарии. Исправляйте в той же ветке новыми коммитами,
  отвечайте на вопросы в комментариях. Когда всё в порядке, владелец одобряет и вливает PR (способ
  «squash»: все ваши коммиты склеиваются в один).
* Вливать PR самим не нужно и нельзя: для этого требуются зелёный CI и одобрение владельца.
* PR должен быть **небольшим**: одно задание, не больше ~400 строк кода (без тестов). Маленькие PR
  проверять проще и быстрее, а ваш вклад виден чётко.

Заготовка описания для бэкенда или фронтенда подставляется автоматически при создании PR.

## 10. Конфликты и ошибки в Git

### 10.1 Конфликт слияния

Бывает, когда вы и кто-то другой изменили **одни и те же строки**. После `git merge origin/main` Git
скажет `CONFLICT` и перечислит файлы. Откройте такой файл: вы увидите куски, подписанные так:

```
<<<<<<< HEAD
ваш вариант строки
=======
чужой вариант строки
>>>>>>> origin/main
```

Что делать:

1. Решите, что должно остаться: ваша строка, чужая или **обе** (чаще всего в общих файлах, таких как
   `router.tsx`, `routes.ts`, `app.ts`, нужно оставить обе строки).
2. Удалите служебные строки `<<<<<<<`, `=======`, `>>>>>>>`. В VS Code над конфликтом есть кнопки
   «Accept Current / Incoming / Both»: можно нажимать их.
3. Сохраните файл и выполните:

   ```bash
   git add <файл>
   git commit --no-edit   # завершить слияние с подписью по умолчанию
   ```

4. Запустите проверки и `git push`.

Не уверены, какой вариант правильный? Не гадайте: напишите владельцу, он объяснит.

### 10.2 Как исправить типичные ошибки

| Ситуация | Что делать |
|----------|-----------|
| Хочу отменить правку файла, которую ещё **не коммитил** | `git restore <файл>` (изменения пропадут навсегда) |
| Убрать файл из набора на коммит (после `git add`) | `git restore --staged <файл>` |
| Забыл переключиться и правил в `main` (коммитить ещё **не** успел) | `git stash`, затем `git checkout -b feature/название`, затем `git stash pop` |
| Нужно срочно переключиться на другую ветку, а правки не готовы | `git stash` (спрятать), потом вернуться и `git stash pop` |
| Хочу посмотреть, что было раньше | `git log --oneline -10` и `git diff` |
| Закоммитил в `main` по ошибке | не делайте `push`; напишите владельцу, он подскажет |
| Не помню, на какой я ветке | `git status` или `git branch` |

### 10.3 Чего **никогда** не делать

* `git push --force` и `git push -f`: перезаписывает историю на GitHub, может уничтожить чужую работу.
* `git reset --hard`: безвозвратно удаляет ваши незакоммиченные изменения; запускайте только если вам это
  сказали.
* Коммитить в `main` напрямую (GitHub всё равно не даст, но не пытайтесь).
* Удалять папку проекта и скачивать заново, «чтобы всё починилось»: сначала пришлите владельцу вывод
  `git status` и `git log --oneline -5`.
* Класть в Git пароли, ключи, файл `.env`, адреса и доступы боевого сервера.

Если что-то пошло не так: **не паникуйте и ничего не удаляйте**. Скопируйте вывод `git status`, текст
ошибки и напишите владельцу. Git хранит историю: почти всё можно вернуть.

> Про предупреждение «LF will be replaced by CRLF»: безобидное, это Windows и Git договариваются о
> символе конца строки. Игнорируйте.

## 11. Правила слаженной работы

Полные правила в [README.md](README.md) этой папки; здесь главное.

1. **Один каталог, один автор.** Правьте только каталоги своей зоны (таблица в README). Нужна правка в
   чужом месте: напишите владельцу.
2. **Общие файлы** (`router.tsx`, `routes.ts`, `sections.ts`, `app.ts`) правятся **одной строкой**; при
   конфликте оставляйте обе строки.
3. **Контракт первым.** Договариваемся о форме данных API (схема, пример JSON, тест) в маленьком первом PR,
   потом сервер и фронтенд делаются параллельно.
4. **Не дублируем** то, что уже есть: шкалы AQI, поиск пропусков, регулярную сетку рядов, графики,
   форматирование. Сначала поищите в `packages/` и в `src/shared/lib`.
5. **Тексты** интерфейса только через i18n, во всех трёх языках (ru, uz, en), в файл своей зоны
   (`map.json`, `analytics.json`).
6. **Логика в чистых функциях с тестами** рядом (`*.test.ts`); компонент только показывает результат.
   Каждую формулу вы должны уметь объяснить на числовом примере: это спросят на защите.
7. **`null` значит «нет показания», а не ноль.**
8. **Миграции базы данных** делает только владелец зоны станций (Тулешов): иначе нумерация миграций
   ломается.
9. **На боевой сервер не ходим**, доступа к нему у вас нет и не нужно; выкатывает владелец.
10. **Каждую неделю** короткая сверка: что сделано, что мешает. Если застряли больше чем на полдня,
    пишите сразу.
11. **Дневник решений:** в описании каждого PR одно-два предложения «что выбрал и почему, какие были
    варианты»: из этого потом собирается глава диплома.

## 12. Работа с ИИ-помощником

Помощник (чат-бот или помощник в редакторе) ускоряет работу, но ошибается, поэтому:

1. **Давайте ему контекст:** файлы `README.md`, `AGENTS.md`, оба `docs/ARCHITECTURE.md`, ваш документ
   заданий и конкретные файлы, с которыми работаете. Готовое вступление для ИИ-помощника есть в
   [README.md](README.md) этой папки, раздел 4.
2. Просите **маленькими шагами** («напиши функцию IDW и тесты к ней»), а не «сделай карту».
3. Просите **объяснять** каждый шаг. Код, который вы не понимаете, на защите не поможет.
4. **Проверяйте результат сами:** запустите, посмотрите в браузере, прогоните тесты. ИИ часто пишет код,
   который выглядит правильно, но не работает или нарушает правила проекта.
5. Не передавайте помощнику пароли, ключи и содержимое `.env`.

## 13. Типичные проблемы

| Симптом | Причина и решение |
|---------|-------------------|
| `pnpm: command not found` или «не является внутренней командой» | не включён pnpm: выполните `corepack enable` (при ошибке прав запустите терминал от администратора) или `npm install -g pnpm`; затем закройте и откройте терминал |
| `node: command not found` или версия ниже 20 | установите Node.js 20 LTS и перезапустите терминал |
| В браузере «Не удалось загрузить данные» | не запущен бэкенд: проверьте http://localhost:8002/v1/health |
| `port 5173 is already in use` | порт занят другой копией: закройте её или `pnpm dev --port 5180` |
| `port is already allocated` (Docker) | порт занят: закройте программу или задайте другой порт (раздел 5.2) |
| `cannot connect to the Docker daemon` или `The system cannot find the file specified` | Docker Desktop не запущен: запустите и дождитесь зелёного Engine running |
| Статус на сайте «данные устарели» | в базе нет свежих точек: запускайте бэкенд с `--profile live` |
| После смены ветки ошибки `Cannot find module` | выполните `pnpm install` |
| Тесты в бэкенде: `ECONNREFUSED` | не запущена база: `docker compose -f docker-compose.dev.yml up -d db` |
| `Refusing to run integration tests...` | это защита: тесты работают только с локальной базой, имя которой оканчивается на `_test` |
| `git push` отклонён: `rejected` | ветка отстала: `git fetch`, `git merge origin/main`, затем `git push` |
| В PR красный CI | откройте Details, прочитайте журнал, воспроизведите ту же команду у себя |
| Сайт выглядит «сломанным» после смены версии | выполните `pnpm install` и перезапустите `pnpm dev` |
